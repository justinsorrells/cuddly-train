  Minor observations (not violations)

  1. invalid_json overloaded for §23 unsupported-type (InboundParser.h:113). A
  valid JSON object with an unsupported type
  (schema/telemetry/response/event/estop_reset) increments invalid_json. §25 has
  no dedicated "invalid message" counter, so this is defensible, but it
  conflates malformed JSON with valid-JSON/wrong-type. Worth a comment or a §25
  note when dispatch lands.
  2. LineFramer buffers at most one active + one pending line.
  Multiple-messages-per-read (§10.4) works only if the service loop interleaves
  acquireLine()/releaseLine() with append() — append early-returns consumed < 
  size when a pending line is waiting. This is the intended zero-copy design,
  but the not-yet-written Phase-4/5 loop must honor it or it will stall the byte
  stream. Flagging so it isn't lost.
  3. CommandContext exposes only seq+args to handlers, not controller_ts/command
  name — correct (echo is library-owned), just noting it's deliberate.

  ## Goal
  The single serialized board-to-controller write path (§13): one path, no
  interleaving, writeFully-equivalent retries bounded by the transmit deadline,
  flush per message. Pure bytes-out over the Transport seam — no message
  building, no scheduling.

  ## Scope
  - read qnethernet-transport, fixed-capacity-cpp first
  - one serialized path over core/Transport.h; telemetry/responses/schema/

    partial writes only until support::kTransmitDeadlineMs, service/yield the
    stack between retries via the injected Clock + Transport, never busy-wait,
    never print()/println() (§13.1, §13.6)

    builders already bound; this is the last guard

    return a fail result (engine closes session + runs controller-loss);
    Telemetry expiry → drop, telemetry_dropped++, track consecutive telemetry
    failures and signal teardown at kTelemetryDeadlineFailuresToTeardown
  - fixed capacity; no allocation; no second serializer
